# UI 信息架构重构策略:双入口 → 单计划中心

> 状态：已实施（历史设计记录） · 2026-06-14 · 当前规范以 `docs/web-ui.md` 和 `PROJECT_STATE.md` 为准

## 0. 结论先行

用户提案(迁移、构建各自独立成页并带进度+选择,二者最终都产出一个「计划」,执行/报告等下游流程都收进计划里)**合理且应采纳**。关键依据:**后端早已是统一计划模型**,前端没收口才造成重复。

- 统一接口:`createEnvironmentPlan(...)` → `applyEnvironmentPlan(...)`
- 统一类型:`EnvironmentPlanType = "migration" | "rebuild" | "change" | "remove" | "repair" | "imported-recipe"`
- build 页已在用 `createEnvironmentPlan`(type=rebuild);migrate 只需产出 type=migration
- 代码里直连执行已标 `@deprecated`,注释明确引导「统一走 createEnvironmentPlan / applyEnvironmentPlan」

提案本质 = 让前端追上后端既定的「生产者→计划→执行/交付」模型。

## 1. 现状证据(重复在哪)

| 工作流阶段 | 当前出现的位置(重复) |
|---|---|
| 执行(apply/runs) | migrate 第 8 步、build 步骤条、plans 页 `runs` tab、顶部流程条「执行」 |
| 报告(report) | migrate 第 9 步、build 第 9 步、plans 页 `reports` tab、**独立「报告」顶级页**、顶部流程条「报告」 |
| 计划(plan) | migrate 第 6 步、build「生成重建计划」、plans 页 `plans` tab |

具体页面结构:
- **Migrate 页**:9 步内嵌流水线 `源主机→分析→选择→未知项→配置/数据→计划→目标/Dry-run→执行→报告`(自己一条龙跑到报告)
- **Build 页**:真实只有 2 个阶段 `select → review`,却额外画了一条**装饰性的 9 步条**「目标主机…验证/报告」;终点调用 `createEnvironmentPlan` 生成计划
- **Plans 页**:tab = `计划 | 执行记录 | 排程 | 漂移 | 外发通知 | 报告`(执行与报告本就在此)
- **Reports 页**:又是独立顶级页
- **顶部 PipelineBar**:6 步 `连接·快照·构建·审查·执行·报告`,点击跳转的就是上面这几个页 ← 与左边栏「流程」分组并排重复

→ 同一工作流被表达了 3~4 遍,用词还不一致(迁移↔连接/快照、计划↔审查/执行)。

## 2. 目标信息架构

### 2.1 左侧边栏分组(重组)
```
工作区
  └ 总览
来源 · 生产计划
  ├ 迁移   ← 入口 A:从真实源环境产出计划
  └ 构建   ← 入口 B:从认证目录产出计划
计划与交付
  └ 计划中心  ← 审查 / 执行 / 验证 / 报告 / 排程 / 漂移 / 通知
治理
  └ 能力管理
```
变更点:
- **移除顶部 PipelineBar**(与边栏重复;全局 6 步概览保留在「总览」页的卡片区)
- **撤销独立「报告」顶级页** → 并入计划中心的 `报告` tab(报告本就是计划执行的产物)

### 2.2 Migrate 页(单页 · 自带进度条 · 终点=生成计划)
阶段(内嵌进度,砍掉下游):
```
① 连接源主机 → ② 采集快照 → ③ 分析 → ④ 选择迁移项 → ⑤ 处理未知/配置 → ⑥ 生成迁移计划
                                                                         ↓ 跳转计划中心
```
- 砍掉现有第 7/8/9 步(目标/Dry-run、执行、报告)——这些移交计划中心
- 终点:`createEnvironmentPlan({ type: "migration", ... })`,成功后跳到计划中心该计划详情

### 2.3 Build 页(单页 · 自带进度条 · 终点=生成计划)
阶段(把装饰条变成真实进度):
```
① 选目标主机 → ② 选已认证能力 → ③ 处理冲突 → ④ 预检 → ⑤ 生成重建计划
                                                          ↓ 跳转计划中心
```
- 删掉装饰性的「执行/验证/报告」步(本就没真跑)
- 保留现有 `select → review` 真实逻辑,终点 `createEnvironmentPlan({ type: "rebuild", ... })`

### 2.4 计划中心(汇聚 · 执行与交付中枢)
单个计划详情内的子流程(线性):
```
审查门禁 → 执行(Dry-run / 真实)→ 验证 → 报告
```
外加运维 tab:`排程 · 漂移 · 外发通知`。报告 = 执行产物,不再单列页面。

## 3. 「选择功能因情形不同」的差异化设定

| | Migrate 的选择 | Build 的选择 |
|---|---|---|
| 数据来源 | 源主机快照里**实际发现**的环境项 | 管理员维护的**认证能力目录** |
| 选什么 | 「要迁移哪些现有东西」(包/服务/配置) | 「要装哪些标准能力」 |
| 特有审查 | 未知项 / 低置信度项 / 配置敏感度 | 能力冲突 / 依赖处理 |
| 证据 | 真实快照证据 | 目录元数据 |
| 产出 | type=`migration` 的计划 | type=`rebuild` 的计划 |

两条路选择体验不同,但**产出统一的 `EnvironmentPlan`**,所以下游(计划中心)用一套逻辑处理两种来源。

## 4. 落地分期(低风险优先)

**阶段一 · 纯收口(低风险,不碰业务逻辑)**
1. 移除顶部 PipelineBar
2. 「报告」独立页并入计划中心 `reports` tab,边栏移除报告项
3. 左边栏按 §2.1 重新分组
→ 可立即做、可独立验收。

**阶段二 · 双入口收尾(中风险)**
4. Migrate 砍第 7/8/9 步,终点改为「生成计划 + 跳转计划中心」
5. Build 把装饰性 9 步条换成真实 5 步进度,终点同上

**阶段三 · 计划中心强化(中风险)**
6. 把计划详情内的 审查→执行→验证→报告 串成清晰线性子流程
7. 普通用户 / admin 的可见范围梳理

## 5. 风险与待核实

- **数据兼容**:已存在的计划(各 type)在计划中心都能正常展示/执行——需回归
- **migrate 现有执行逻辑**:第 7/8/9 步若已有真实后端调用,迁移到计划中心时不能丢功能(需逐行核对 MigratePipelinePage 的 target/apply/report 实现)
- **权限**:普通用户只看认证能力 / 不能真实执行的门禁,需在新结构里保持
- **深链接**:`/app/reports`、`/app/plans?tab=runs` 等旧路径要做重定向,避免书签失效
